# Research logging workflow

## Purpose

The canonical log serves two audiences simultaneously:

- an AI or human resuming one research problem; and
- a future statistical analysis across many problems, models, outcomes,
  verification methods, and human interventions.

The design therefore favors append-only facts, controlled vocabulary, explicit
missingness, and source provenance over a polished retrospective narrative.
The human-readable progress file remains free-form; the event ledger is compact
and machine-oriented.

## Why one ledger per problem

Each problem owns:

```text
logs/<problem-id>/
├── problem.json       stable metadata
├── progress.md|tex    human-readable state
├── state.jsonl        canonical append-only ledger
├── raw/               source material worth retaining
├── inbox/             temporary AI event drafts
└── recovery/          generated recovery manifests/prompts
```

Per-problem ledgers keep patches local, avoid a global write bottleneck, and
make a problem portable. Cross-problem datasets are generated by streaming all
ledgers; no duplicate warehouse is committed.

## Canonical event model

Every `state.jsonl` line is one compact JSON object. The package supplies:

- `schema_version`;
- a globally unique `event_id`;
- `problem_id`;
- monotone per-problem `sequence`;
- UTC `recorded_at`;
- `prev_event_hash` and `event_hash`.

The author supplies a short `summary`, `event_type`, and any relevant context:

- `occurred_at` plus `temporal_precision` when historical timing is known;
- `stage` and `outcome`;
- `run_id`;
- `actor` and `subject`;
- subjective `metrics`;
- structured `evidence` and `artifacts`;
- `dependencies`, `tags`, event-specific `data`, and `provenance`.

The hash chain detects accidental edits or omitted middle lines. It is an
integrity check, not a cryptographic identity or timestamping service.

## First-time setup

Python 3.10 or later is sufficient. Installation is optional:

```bash
python -m researchlog --help
# or
python -m pip install -e .
researchlog --help
```

Register a new problem prospectively, before its outcome is known:

```bash
python -m researchlog init problem-0002-example \
  --title "Example research problem" \
  --source-ref problems/example.tex \
  --domain mathematics --tag hypocoercivity \
  --actor-type human --actor-name "repository maintainer"
```

To register a legacy non-empty problem directory without overwriting its human
log:

```bash
python -m researchlog init problem-legacy \
  --title "Legacy problem" --human-log legacy-progress.tex \
  --source-ref logs/problem-legacy/legacy-progress.tex \
  --adopt-existing --registration-mode retrospective \
  --actor-type human --actor-name "repository maintainer"
```

Problem identifiers are permanent. Do not encode mutable status or model names
in them. `metadata.registration_mode` distinguishes prospective, retrospective,
recovered, and unknown registration so later analyses can account for selection
bias.

## One normal research run

Before assigning a model, obtain a compact current-state and protocol summary:

```bash
python -m researchlog brief problem-0002-example
```

Start the run:

```bash
python -m researchlog begin problem-0002-example \
  --objective "Resolve part (a), or isolate the exact obstruction" \
  --input-ref problems/example.tex \
  --actor-type ai --actor-name ChatGPT \
  --provider OpenAI --model "exact-model-version" \
  --interface chatgpt-pro --independent
```

The command prints a `RUN_ID`. Use it for related records. A compact claim
record can be created with flags:

```bash
python -m researchlog record problem-0002-example \
  --type claim.created --run-id "$RUN_ID" \
  --stage synthesize --outcome partial \
  --subject-type claim --subject-id claim-example \
  --summary "A candidate identity reduces the problem to one unresolved lemma." \
  --confidence 0.55 --impact-score 1 \
  --data '{
    "claim_status":"candidate",
    "verification_status":"unverified",
    "novelty_status":"unknown",
    "remaining_gap":"Prove the reduction under multiplicity."
  }'
```

For several records, JSONL is safer and shorter than repeated shell flags:

```bash
python -m researchlog template problem-0002-example > /tmp/run.jsonl
# edit the drafts, then
python -m researchlog ingest problem-0002-example --file /tmp/run.jsonl
```

The template defaults to `independent = false` because it incorporates existing
problem metadata. Use `--independent` only for a genuinely blind attempt. All
`REPLACE_*` markers must be edited; ingestion rejects unedited placeholders.

End every run, including failed ones:

```bash
python -m researchlog end problem-0002-example \
  --run-id "$RUN_ID" --outcome partial --reason completed \
  --capture-completeness complete --protocol-complete \
  --summary "The reduction survived numerical tests; the multiplicity lemma remains open." \
  --next-action "Assign an independent adversarial proof audit."
```

## Patch workflow for ChatGPT Pro or another remote model

A remote model often cannot append safely to the user's local hash chain. In
that case its patch should add:

```text
logs/<problem-id>/inbox/<run-id>.jsonl
```

The file contains event drafts only. After applying the patch:

```bash
python -m researchlog ingest-inbox <problem-id>
python -m researchlog validate <problem-id>
python -m researchlog doctor <problem-id>
```

The package validates the whole batch before taking the ledger lock, then fills
canonical fields, links the hash chain, flushes the append, and removes the
inbox file only after success. A failed ingest leaves the draft untouched. The
input SHA-256 makes ingestion idempotent: if append succeeds but deletion is
interrupted, retrying the same bytes returns the existing events instead of
appending duplicates. A partial prior batch is treated as corruption and routed
to validation/recovery rather than guessed around.

## Human interventions and selection

Human involvement is a primary analytical variable, not editorial noise.
Record interventions when a person:

- chooses or reformulates a problem;
- supplies a definition, paper, method, example, or counterexample;
- corrects an argument or code;
- changes compute or search resources;
- stops, restarts, or redirects a run;
- decides to distill or publish a result.

Use `human.intervention` and a controlled `data.intervention_type`. Selection
must additionally use `selection.recorded`. This permits later analysis of how
much research value came from model generation versus human routing and how
strongly post-selection shapes the visible outputs.

## Evidence and verification

Evidence is an array because one claim can have independent channels. Each
entry records a type, result, independence flag, optional strength, and artifact
path. Examples include formal proof audit, Lean kernel acceptance, symbolic
algebra, numerical stress tests, literature search, and counterexample search.

Use a separate `verification.recorded` event when the check itself is a
substantive action. Never encode “the proof looks correct” as formal
verification. For Lean, record toolchain/version, exact file path, command, and
kernel result in `data`.

## Artifacts

`researchlog snapshot` stores repository-relative path, SHA-256, byte size, and
MIME type in an `artifact.recorded` event:

```bash
python -m researchlog snapshot problem-0002-example \
  --path logs/problem-0002-example/progress.tex --role human_log \
  --path promising-approaches/example.tex --role promising_note
```

Long transcripts, generated proofs, code, numerical output, and figures belong
in files. Event summaries should remain short and decision-relevant.

## Validation and diagnostics

```bash
python -m researchlog validate
python -m researchlog doctor
```

`validate` checks metadata, JSON, controlled fields, event order, IDs, the hash
chain, run pairing, annotation targets, artifact snapshots, and pending inbox
files. `doctor` additionally applies `schemas/analytics-profile-v1.json` and
reports fields that future cross-problem analysis expects.

Warnings are intentionally visible but do not make ordinary validation fail.
Use `--strict` in a release/paper-candidate branch. A protocol gap should usually
be logged rather than hidden merely to make strict mode green.

## Analysis exports

Canonical JSONL remains the only source of truth. Generate disposable datasets:

```bash
python -m researchlog export --output data/exports/latest --overwrite
python -m researchlog stats
```

Problem rows expose registration mode and whether a legacy directory was adopted
as direct columns in addition to the full metadata JSON. The default export
contains:

- `problems.csv` and `problems.jsonl`;
- `events.csv` and `events.jsonl`;
- `artifacts.csv`;
- `evidence.csv`;
- `annotations.csv`;
- `researchlog.sqlite` with indexes on problem/event type, run, and model;
- `dataset-manifest.json` with source-ledger hashes and row counts.

Exports flatten stable dimensions but retain event-specific payloads as JSON.
This avoids schema loss while remaining immediately usable in Python, R, SQL,
or a spreadsheet.

## Schema evolution and annotations

Never rewrite historic events merely because a new statistical question needs a
field that was not part of the original protocol. Append `annotation.added`:

```json
{
  "event_type":"annotation.added",
  "summary":"Recovered the historical model interface from the raw transcript header.",
  "stage":"recover",
  "outcome":"partial",
  "data":{
    "target_event_id":"evt_...",
    "set":{"actor.interface":"chatgpt-pro"},
    "reason":"Required by analytics profile v2."
  },
  "provenance":{
    "mode":"recovery",
    "source_refs":["logs/problem-x/raw/session.md#header"],
    "extraction_confidence":0.98,
    "review_status":"unreviewed",
    "recovery_bundle_id":"recovery_..."
  }
}
```

Exports materialize overlays while retaining the original and annotation events.
Immutable identifiers, sequence, timestamps, and hashes cannot be annotated.

## Recovery when the protocol failed

Run one problem, or prepare all currently detected gaps:

```bash
python -m researchlog recover prepare <problem-id>
python -m researchlog recover prepare-all
```

`prepare-all` selects problems with an explicit `protocol.gap` requesting
recovery or with validation/analytics-profile gaps; pass `--all` to force a
bundle for every registered problem. Each bundle contains:

- a hashed inventory of the problem statement, human/raw logs, canonical ledger,
  schemas, and protocol documents;
- ledger validation failures and analytics-profile gaps;
- an extraction prompt designed for a frontier model;
- an example recovered event.

The model must chase every listed file and produce source-grounded JSONL. It may
append missing historical events, add overlays to existing events, or declare
irrecoverable fields with `protocol.gap`. When a reviewed recovery resolves a
previous gap, its annotation should set `data.recovery_recommended = false` on
that gap; repository-wide preparation respects reviewed overlays. The model must
not guess unavailable timestamps, models, resources, interventions, novelty, or
verification.

After inspection:

```bash
python -m researchlog recover ingest <problem-id> \
  --bundle <bundle-id> --file recovered-events.jsonl \
  --review-status human_reviewed
```

Native and recovered observations remain distinguishable in every export. This
allows sensitivity analyses that exclude unreviewed or low-confidence recovery.

If an interrupted append left a non-newline-terminated final fragment, first
quarantine only that fragment:

```bash
python -m researchlog repair <problem-id> --truncate-invalid-tail
```

The command never attempts to silently repair arbitrary middle-of-ledger damage.

## Statistical cautions

The ledger improves observability; it does not by itself eliminate bias.
Meaningful comparisons require prospective registration where possible,
explicit retrospective registration for legacy material, logging all attempts,
preserving model/version and resource changes, and recording human selection.
Subjective confidence and impact scores are ordinal annotations unless
separately calibrated. Recovered observations should be analyzed both included
and excluded.
